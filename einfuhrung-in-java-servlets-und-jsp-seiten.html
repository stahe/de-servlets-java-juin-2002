    3. Einführung in Java-Servlets und JSP-Seiten

    In diesem Kapitel finden sich verschiedene Beispiele für Servlets und JSP-Seiten. Sie wurden mit dem Tomcat-Server getestet. Dieser läuft auf Port 8080. Über die Links auf der Startseite gelangt man zu Beispielen für Servlets und JSP-Seiten. Die folgenden Beispiele stammen größtenteils aus den Tomcat-Beispielen. Um sie zu testen, starten Sie einfach Tomcat, rufen Sie die Seite URL http://localhost:8080 mit einem Browser auf und folgen Sie dem Link zu den Servlets.

    3.1. Java-Servlets

    3.1.1. Inhalte an einen Web-Client senden

    Wir betrachten das obige „Hello World“-Beispiel. Das Servlet lautet wie folgt: 

    
import java.io.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class HelloWorld extends HttpServlet {

    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<html>");
        out.println("<head>");
        out.println("<title>Hello World!</title>");
        out.println("</head>");
        out.println("<body>");
        out.println("<h1>Hello World!</h1>");
        out.println("</body>");
        out.println("</html>");
    }
}

import javax.servlet.*;
import javax.servlet.http.*;

    Die Bibliothek javax.servlet ist nicht immer standardmäßig im JDK enthalten. In diesem Fall kann man sie direkt von der Sun-Website herunterladen.

public class HelloWorld extends HttpServlet {
    • Eine an das Servlet gerichtete Anfrage GET wird von der Methode doGet verarbeitet 
    
    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    • Ebenso wird eine an das Servlet gerichtete Anfrage POST von der Methode doPost verarbeitet 
    
    public void doPost(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException

    • Das Objekt response ermöglicht es uns, die HTTP-Header festzulegen, die an den Client gesendet werden. Beispielsweise wird der Header „Content-Type: text/html“ hier wie folgt festgelegt: 
            response.setContentType("text/html");
    • Um die Antwort an den Client zu senden, verwendet das Servlet einen Ausgabestrom, der ihm vom Objekt response bereitgestellt wird: 
            PrintWriter out = response.getWriter();
    • Sobald dieser Ausgabestrom vorliegt, wird der Code „HTML“ darin geschrieben und somit an den Client gesendet: 
            out.println("<html>");
        out.println("<body>");
        out.println("<head>");
        out.println("<title>Hello World!</title>");
        out.println("</head>");
        out.println("<body>");
        out.println("<h1>Hello World!</h1>");
        out.println("</body>");
        out.println("</html>");

    Das folgende Beispiel zeigt, wie ein Servlet vom Web-Client gesendete Parameter abrufen kann. Ein Eingabeformular:

    Der Quellcode des Servlets lautet wie folgt:

    
import java.io.*;
import java.util.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class myRequestParamExample extends HttpServlet {

    String title="Récupération des paramètres d'un formulaire";

    public void doGet(HttpServletRequest request,
                      HttpServletResponse response)
        throws IOException, ServletException
    {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<html>");
        out.println("<body>");
        out.println("<head>");
        out.println("<title>" + title + "</title>");
        out.println("</head>");
        out.println("<body bgcolor=\"white\">");
        out.println("<h3>" + title + "</h3>");
        String firstName = request.getParameter("firstname");
        String lastName = request.getParameter("lastname");
        if (firstName != null || lastName != null) {
            out.println("firstname= " + firstName + "<br>");
            out.println("lastname= " + lastName);
        } else {
            out.println("pas de paramètres");
        }
        out.println("<P>");
        out.print("<form action=\"RequestParamExample\" method=\"POST\">");
        out.println("firstname= <input type=text size=20 name=firstname>");
        out.println("<br>");
        out.println("lastname= <input type=text size=20 name=lastname>");
        out.println("<br>");
        out.println("<input type=submit>");
        out.println("</form>");
        out.println("</body>");
        out.println("</html>");
    }

    public void doPost(HttpServletRequest request,
                      HttpServletResponse response)
        throws IOException, ServletException
    {
        doGet(request, response);
    }

}

    Im Vergleich zum vorherigen Beispiel sind folgende Neuerungen zu beachten:

    • Die vom Browser gesendeten Parameter werden wie folgt abgerufen: 
    
        String firstName = request.getParameter("firstname");
        String lastName = request.getParameter("lastname");

    Die Methode request.getParameter("nomParamètre") gibt den Zeiger null zurück, wenn der Parameter nomParamètre nicht zu den vom Web-Client gesendeten Parametern gehört.

    • Das Formular gibt an, dass der Browser die Parameter über die Methode POST senden muss 
            out.print("<form action=\"RequestParamExample\" method=\"POST\">");
    • Die empfangenen Parameter werden von der Methode doPost des Servlets verarbeitet. Hier beschränkt sich diese Methode darauf, die Methode doGet aufzurufen. Somit verarbeitet dieses Servlet die Werte des Formulars, unabhängig davon, ob sie von einem GET oder einem POST gesendet wurden. 
    
    public void doPost(HttpServletRequest request,
                      HttpServletResponse response)
        throws IOException, ServletException
    {
        doGet(request, response);
    }

    3.1.3. Die von einem Web-Client gesendeten HTTP-Header abrufen

    Das folgende Servlet zeigt, wie die vom Web-Client gesendeten HTTP-Header abgerufen werden können:

    Der Quellcode des Servlets lautet wie folgt:

    
import java.io.*;
import java.util.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class RequestHeaderExample extends HttpServlet {

    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        Enumeration e = request.getHeaderNames();
        while (e.hasMoreElements()) {
            String name = (String)e.nextElement();
            String value = request.getHeader(name);
            out.println(name + " = " + value);
        }
    }
}

    Wichtige Hinweise:

    • Über das Objekt request und dessen Methode getHeaderNames erhalten wir Zugriff auf die vom Browser gesendeten HTTP-Header in Form einer Aufzählung: 
            Enumeration e = request.getHeaderNames();
    • Mit der Methode request.getHeader("Header") lässt sich ein bestimmter HTTP-Header abrufen. Das obige Beispiel zeigt einige davon. Es sei daran erinnert, dass die hier vorgestellten Header vom Browser gesendet werden. Der Server verfügt ebenfalls über eigene HTTP-Header, die manchmal diejenigen des Browsers übernehmen. Die vom Browser gesendeten HTTP-Header dienen dazu, den Server über die Fähigkeiten des Browsers zu informieren.
    Header
    Bedeutung
    User-Agent
    Identität des Browsers
    Accept
    Die vom Browser unterstützten Formate MIME. So bedeutet image/gif, dass der Browser Bilder im Format GIF verarbeiten kann
    Host
    im Format hote:port. Gibt an, welchen Rechner und welchen Port der Browser kontaktieren möchte.
    Accept-Encoding
    Vom Browser akzeptiertes Kodierungsformat für vom Server gesendete Dokumente. Wenn ein Server also ein Dokument in normaler, unkomprimierter Form und eines im komprimierten gzip-Format bereitstellt und der Browser angegeben hat, dass er das gzip-Format verarbeiten kann, kann der Server das Dokument im gzip-Format senden, um Bandbreite zu sparen.
    Accept-language
    Vom Browser akzeptierte Sprachen. Verfügt ein Server über dasselbe Dokument in mehreren Sprachen, sendet er eine Version, deren Sprache vom Browser akzeptiert wird.
    Referer
    die vom Browser angeforderte URL
    Connection
    die vom Browser angeforderte Verbindungsart. Keep-alive bedeutet, dass der Server die Verbindung nicht trennen darf, nachdem er die angeforderte Seite an den Browser übermittelt hat. Stellt der Browser fest, dass die empfangene Seite beispielsweise Links zu Bildern enthält, kann er neue Anfragen an den Server senden, um diese abzurufen, ohne eine neue Verbindung herstellen zu müssen. Der Browser übernimmt dann die Initiative, die Verbindung zu schließen, sobald er alle Elemente der Seite empfangen hat.

    3.2.7. Bereitstellung und Debugging von JSP-Seiten auf dem Tomcat-Server

    Wenn man eine Seite JSP erstellen und mit dem Tomcat-Server verwenden möchte, stellt sich die Frage, wo die Seite in der Verzeichnisstruktur des Servers abgelegt werden soll. Es gibt verschiedene Möglichkeiten, auf die wir später noch eingehen werden. Vorerst ist es am einfachsten, die Seite JSP in einem Ordner der Verzeichnisstruktur <tomcat>\webapps\examples\jsp (Tomcat 4.x) abzulegen, wobei <tomcat> das Installationsverzeichnis von Tomcat ist. So lautete beispielsweise die Adresse für URL aus dem vorherigen Beispiel http://localhost:8080/examples/jsp/perso/tintin/tintin.jsp. Das bedeutet, dass sich die Seite tintin.jsp im Ordner <tomcat>\webapps\examples\jsp\perso\tintin befand.

    Eine Seite mit dem Namen JSP wird in eine Java-Quelldatei übersetzt, die anschließend von Tomcat kompiliert wird, wenn die Seite JSP (mit der ID URL) von einem Browser angefordert wird. Dabei können Kompilierungsfehler auftreten. Tomcat meldet diese in seiner Antwort an den Browser. Dabei werden insbesondere die fehlerhaften Zeilen der .java-Datei angegeben. Die Fehler können verschiedene Ursachen haben:

    1. Der Code JSP der Seite ist fehlerhaft (z. B. Fehler in den verwendeten JSP-Tags)
    2. der in die Seite eingebundene Java-Code JSP ist fehlerhaft

    Die erste Ursache lässt sich durch Überprüfung des JSP-Codes der Seite beheben. Die zweite Ursache lässt sich durch Überprüfung des Java-Codes beheben. Dies kann erfolgen, indem die für die Seite JSP generierte .java-Datei direkt mit einem Tool wie JBuilder kompiliert wird, das erweiterte Debugging-Funktionen bietet, die über die von Tomcat hinausgehen.

    3.3.1. Die Konfigurationsdateien server.xml und web.xml

    Bisher haben wir zum Testen unserer Servlets und Seiten JSP

    • die Servlets im Ordner <tomcat>\webapps\examples\WEB-INF\classes abgelegt. Sie waren dann über die URL URL http://localhost:8080/examples/servlet/nomServlet
    • die Seiten JSP im Verzeichnisbaum <tomcat>\webapps\examples\jsp. Sie waren damals über die Seite URL http://localhost:8080/examples/jsp/nomPageJSP erreichbar

    Wir haben nie erklärt, warum das so war. Die Konfiguration des Tomcat-Servers erfolgt in einer Textdatei namens server.xml, die sich im Ordner <tomcat>\conf befindet:

    Diese Textdatei ist eigentlich eine XML-Datei (eXtended Markup Language). Ein XML-Dokument ist ein Textdokument, das Tags enthält, genau wie ein HTML-Dokument. Während jedoch die Tags der Sprache HTML klar definiert sind, ist dies bei denen der Sprache XML nicht der Fall. Somit ist das folgende Dokument ein XML-Dokument:

    <personne>
    <prenom>Pierre</prenom>
  <nom>Lucas</nom>
  <age>28</age>
</personne>

    Ein XML-Dokument ist einfach ein „ausgezeichnetes“ Dokument, das bestimmten Auszeichnungsregeln folgt:

    • Ein Text, der in der Form <xx att1="val1" att2="val2" ....>Text</xx> markiert ist
    • Ein Tag kann auch allein stehen und die Form <xx att1="val1" att2="val2" ..../> haben

    Die Felder „atti“ werden als Attribute des Tags „xx“ bezeichnet, und die Felder „vali“ sind die diesen Attributen zugeordneten Werte. Manche HTML-Dokumente sind keine gültigen XML-Dokumente. Beispielsweise ist das HTML-Tag <br> kein gültiges XML-Tag. Es müsste wie folgt geschrieben werden: <br/>, um gültig zu sein und die Regel einzuhalten, wonach jedes XML-Tag geschlossen werden muss. Eine Variante von HTML namens XHTML wurde erstellt, um jedes XHTML-Dokument zu einem gültigen XML-Dokument zu machen. Einige der neueren Browser sind in der Lage, XML-Dateien anzuzeigen. Wenn wir also das oben als Beispiel gezeigte Dokument XML als personne.xml bezeichnen und es mit IE6 anzeigen, erhalten wir folgende Darstellung:

    IE6 erkennt die Tags und färbt sie ein. Anhand der Tags erkennt es auch die Struktur des Dokuments. Wenn wir also das folgende Dokument als personne2.xml bezeichnen:

    <personne><prenom>Pierre</prenom><nom>Lucas</nom><age>28</age></personne>

    und es mit IE6 anzeigen, erhalten wir dieselbe Darstellung:

    IE6 hat die Struktur und den Inhalt des Dokuments korrekt erkannt. Der ganze Vorteil des Dokuments XML liegt in dieser Eigenschaft: Es ist einfach, die Struktur und den Inhalt eines Dokuments XML wiederzufinden. Dies geschieht mit einem Programm, das als XML-Parser bezeichnet wird. XML-Dokumente entwickeln sich zunehmend zum Standard beim Dokumentenaustausch im Internet. Nehmen wir an, ein Rechner A soll ein DOC-Dokument an einen Rechner B senden. Das DOC-Dokument wird aus den Informationen einer DB-A-Datenbank erstellt. Rechner B muss das Dokument DOC in einer Datenbank DB-B speichern. Der Austausch kann wie folgt erfolgen:

    • Maschine A ruft die Daten aus der Datenbank DB-A ab und kapselt diese in ein Textdokument XML ein
    • Das Dokument XML wird über das Netzwerk an Maschine B gesendet
    • Rechner B analysiert das empfangene Dokument mit einem Parser XML und extrahiert daraus sowohl die Struktur als auch die Daten (wie es IE6 in unserem Beispiel getan hat). Anschließend kann er die empfangenen Daten in der Datenbank DB-B speichern

Wie wir zuvor gesehen haben, befindet sich dieser im Ordner <tomcat>\webapps\examples.
    • Tomcat verwendet den Rest des Servlet-Pfads, um das Servlet in der Webanwendung examples zu finden. Dieser Pfad /servlet/servletToJsp gibt an, dass das Servlet mit dem Namen servletToJsp ausgeführt werden soll. Tomcat liest daraufhin die Konfigurationsdatei web.xml der Anwendung examples, die sich unter <tomcat>\webapps\examples\WEB-INF befindet. In dieser Datei stellt er fest, dass das Servlet servletToJsp mit der Java-Klasse servletToJsp verknüpft ist (siehe Datei web.xml oben). Anschließend sucht er diese Klasse im Ordner „WEB-INF\classes“ der Webanwendung „examples, c.a.d“. in <tomcat>\webapps\examples\WEB-INF\classes und führt sie aus.

    3.3.7. Zusammenarbeit von Servlets und Seiten JSP innerhalb einer Webanwendung

    Wenn ein Client eine Anfrage an einen Webserver sendet, kann die Antwort von mehreren Servlets und Seiten (JSP) zusammengestellt werden. Bislang wurde die Antwort von einem einzigen Servlet oder einer einzigen Seite (JSP) zusammengestellt. Wir haben gesehen, dass die Seite JSP eine bessere Lesbarkeit der Struktur des generierten Dokuments HTML ermöglicht. Allerdings enthält sie in der Regel auch viel Java-Code. Man kann dies verbessern, indem man

    • den Java-Code, der nicht den HTML-Code der Antwort generiert, in ein oder mehrere Servlets
    • in Seiten JSP den Code zur Generierung der verschiedenen Dokumente HTML, die als Antwort an den Client gesendet werden

    Auf diese Weise lässt sich hoffentlich die Trennung zwischen Java-Code und HTML-Code verbessern.     3.4.2. Synchronisation der Anfragen mit einem Servlet

    Kehren wir zur vorherigen Seite JSP zurück, die einen Zähler inkrementiert und diesen an den Web-Client zurückgibt. Nehmen wir an, es liegen zwei gleichzeitige Anfragen vor. Dann werden zwei Threads erstellt, um diese auszuführen; diese Threads nutzen dieselbe Servlet-Instanz und somit hier denselben Zähler. Hier noch einmal der Code, der den Zähler inkrementiert:

    
  public int getCompteur(){
     // Der Zähler wird erhöht
    int myCompteur=compteur;
    myCompteur++;
    compteur=myCompteur;
     // wird zurückgegeben
    return compteur;
  }

    Die Inkrementierung des Zählers wurde absichtlich ungeschickt geschrieben. Nehmen wir an, die Ausführung der beiden Threads verläuft wie folgt:

     
    1. Zum Zeitpunkt T1 wird der Thread TH1 ausgeführt. Er liest den Zähler (=145) in myCompteur aus, wird dann unterbrochen und verliert die Prozessorsteuerung. Er hatte also keine Zeit, myCompteur zu inkrementieren und den neuen Wert in compteur zu kopieren.
    2. Zu diesem Zeitpunkt wird der Thread T2 ausgeführt. Er liest den Zähler (=145) aus myCompteur aus, wird dann unterbrochen und verliert die Prozessorsteuerung. Es ist zu beachten, dass die beiden Threads unterschiedliche Variablen myCompteur haben. Sie teilen sich lediglich die Instanzvariablen, also diejenigen, die für alle Methoden global sind.
    3. Zum Zeitpunkt T3 übernimmt der Thread TH1 wieder die Kontrolle und wird beendet. Er gibt daher 146 an seinen Client zurück.
    4. Zum Zeitpunkt T4 übernimmt der Thread TH2 wieder die Kontrolle und beendet seine Ausführung. Auch er gibt 146 an seinen Client zurück, obwohl er eigentlich 147 hätte zurückgeben müssen.

    Hier liegt ein Problem bei der Thread-Synchronisation vor. Wenn TH1 den Zähler erhöhen will, müsste verhindert werden, dass ein anderer Thread dies ebenfalls tut. Um dieses Problem zu verdeutlichen, schreiben wir die Seite JSP wie folgt um:

    <html>
  <head>
    <title>Compteur synchronisé</title>
  </head>
  <body>
    Compteur= <%= getCompteur() %>
  </body>
</html>

  public int getCompteur(){
     // Der Zähler wird ausgelesen
    int myCompteur=compteur;
     // 10 Sekunden Pause
    try{
      Thread.sleep(10000);
    }catch (Exception ignored){}
     // Zähler wird erhöht
    compteur=myCompteur+1;
     // den Wert zurückgeben
    return compteur;
  }

  public void jspInit(){

    Hier haben wir den Thread dazu gezwungen, 10 Sekunden nach dem Auslesen des Zählers anzuhalten. Er sollte daher die Prozessorauslastung freigeben, sodass ein anderer Thread seinerseits einen Zähler auslesen kann, der nicht inkrementiert wurde. Wenn wir Anfragen mit einem Browser stellen, sehen wir keinen Unterschied, abgesehen von der Wartezeit von 10 Sekunden, bis wir das Ergebnis erhalten.

    import java.net.*;
import java.util.regex.*;
import java.io.*;

public class clientCompteurJSP {

    public static void main(String[] params){

         // Daten
        String syntaxe="Syntaxe : pg URL nbAppels";

         // Parameterprüfung
        if(params.length!=2){
            System.err.println(syntaxe);
            System.exit(1);
        }//if
         // URL
        URL urlCompteur=null;
        try{
            urlCompteur=new URL(params[0]);
            String query=urlCompteur.getQuery();
            if(query!=null) throw new Exception();
        }catch (Exception ex){
            System.err.println(syntaxe);
            System.err.println("URL ["+params[0]+" incorrecte");
            System.exit(2);
        }//try-catch
         // Anzahl der Aufrufe
        int nbAppels=0;
        try{
            nbAppels=Integer.parseInt(params[1]);
            if(nbAppels<=0) throw new Exception();
        }catch(Exception ex){
            System.err.println(syntaxe);
            System.err.println("Nombre d'appels ["+params[1]+" incorrect");
            System.exit(3);
        }//try-catch

         // Die Parameter sind korrekt – die Verbindungen zu URL können hergestellt werden
        try{
            getCompteurs(urlCompteur,nbAppels);
        }catch(Exception ex){
            System.err.println(syntaxe);
            System.err.println("L'erreur suivante s'est produite : "+ex.getMessage());
            System.exit(4);
        }//try-catch
    }//main

    private static void getCompteurs (URL urlCompteur, int nbAppels)
            throws Exception {
         // führt nbAppels zum URL urlCompteur aus
         // zeigt jedes Mal den vom Webserver zurückgegebenen Zählerwert an


         // aus urlCompteur werden die für die Verbindung zum Steuer-Server erforderlichen Informationen entnommen
        String path=urlCompteur.getPath();
        if(path.equals("")) path="/";
        String host=urlCompteur.getHost();
        int port=urlCompteur.getPort();
        if(port==-1) port=urlCompteur.getDefaultPort();

         // Es werden die Aufrufe an URL durchgeführt
        Socket[] clients=new Socket[nbAppels];
        for(int i=0;i<nbAppels;i++){
             // Es wird eine Verbindung zum Server hergestellt
            clients[i]=new Socket(host,port);
             // Es wird ein Schreib-Stream zum Server erstellt
            PrintWriter OUT=new PrintWriter(clients[i].getOutputStream(),true);
             // Anforderung des URL – Senden der Kopfdaten HTTP
            OUT.println("GET " + path + " HTTP/1.1");
            OUT.println("Host: " + host + ":" + port);
            OUT.println("Connection: close");
            OUT.println("");
        }//für

         // lokale Daten
        String réponse=null;                        // Antwort des Servers
         // das gesuchte Muster in der Antwort HTML des Servers
        Pattern modèleCompteur=Pattern.compile("^\\s*Compteur= (\\d+)");
         // das Muster einer korrekten Antwort
        Pattern réponseOK=Pattern.compile("^.*? 200 OK");
         // das Ergebnis des Vergleichs mit dem Muster
        Matcher résultat=null;

        for(int i=0;i<nbAppels;i++){
             // Jeder Client liest die Antwort, die ihm der Server sendet

             // Es werden die Ein- und Ausgabeströme des Clients erstellt: TCP
            BufferedReader IN=new BufferedReader(new InputStreamReader(clients[i].getInputStream()));

             // Die erste Zeile der Antwort wird gelesen
            réponse=IN.readLine();
             // Die Zeile HTTP wird mit dem Muster der korrekten Antwort verglichen
            résultat=réponseOK.matcher(réponse);
            if(! résultat.find()){
                 // Es liegt ein Problem mit URL vor
                throw new Exception("Client n° " + i + " - Le serveur a répondu : URL ["+ urlCompteur + "] inconnue");
            }//if

             // wird die Antwort bis zum Ende der Kopfzeilen gelesen
            while((réponse=IN.readLine())!=null && ! réponse.equals("")){
            }//während

             // die Header sind fertig HTTP – wir gehen zum Code über HTML
             // um den Zählerstand abzurufen
            boolean compteurTrouvé=false;
            while((réponse=IN.readLine())!=null){
                 // die Zeile wird mit dem Zählermuster verglichen
                if(! compteurTrouvé){
                    résultat=modèleCompteur.matcher(réponse);
                    if(résultat.find()){
                         // Zähler gefunden
                        System.out.println("Compteur="+résultat.group(1));
                        compteurTrouvé=true;
                    }//if
                }//if
            }//while

             // Fertig
            clients[i].close();
        }//for
    }//getCompteurs

    Erläutern wir den obigen Code:

    • Das Programm akzeptiert zwei Parameter:
      • die URL der Seite JSP des Zählers
      • die Anzahl der Kunden, die für diese URL angelegt werden sollen
    • Das Programm überprüft daher zunächst die Gültigkeit der Parameter: ob tatsächlich zwei vorhanden sind, ob der erste syntaktisch einem URL entspricht und ob der zweite eine ganze Zahl > 0 ist. Um zu überprüfen, ob der URL syntaktisch korrekt ist, verwenden wir die Klasse URL und ihren Konstruktor URL (String), der ein Objekt URL aus einer Zeichenkette wie http://istia.univ-angers.fr erstellt. Es wird eine Ausnahme ausgelöst, wenn die Zeichenkette kein syntaktisch gültiges URL ist. Auf diese Weise können wir die Gültigkeit des ersten Parameters überprüfen.
    • Sobald die Parameter überprüft wurden, wird die Kontrolle an die Prozedur getCompteurs übergeben. Diese erstellt nbAppels-Clients, die sich alle gleichzeitig (oder fast gleichzeitig) mit dem URL urlCompteur verbinden.
    • Der Port und der Rechner, mit dem sich die Clients verbinden sollen, werden aus den Prozeduren URL und urlCompteur entnommen: [URL].Mit getHost() lässt sich der Name des Rechners ermitteln, und mit [URL].getPort() lässt sich der Port ermitteln.
    • Eine erste Schleife ermöglicht es jedem Client:
      • eine Verbindung zum Webserver herzustellen
      • eine Anfrage an den Server zu stellen

    In dieser Schleife wartet der Client nicht auf die Antwort des Servers. Denn das Ziel ist es, den Server dazu zu bringen, nahezu gleichzeitige Anfragen zu empfangen.

    • Eine zweite Schleife ermöglicht es jedem Client, die vom Server gesendete Antwort zu empfangen und zu verarbeiten. Die Verarbeitung besteht darin, in der Antwort die Zeile zu finden, die den Zählerstand enthält, und diese anzuzeigen.

    Um das zuvor aufgezeigte Problem (derselbe Zähler wird an alle fünf Clients gesendet) zu lösen, müssen wir die Threads des Zählerservices auf ein und dasselbe Objekt synchronisieren, bevor wir in den kritischen Abschnitt zum Lesen und Aktualisieren des Zählers eintreten. Die neue Seite JSP sieht wie folgt aus:

    
<html>
  <head>
    <title>Compteur synchronisé</title>
  </head>
  <body>
    Compteur= <%= getCompteur() %>
  </body>
</html>

<%!
   // globale Variablen und Methoden der Seite JSP
  
   // Instanzvariablen
  int compteur;
  Object verrou=new Object();
  
   // Methode zum Inkrementieren des Zählers  
  public int getCompteur(){
  
     // Der kritische Abschnitt wird synchronisiert
    synchronized(verrou){
       // Der Zähler wird gelesen
      int myCompteur=compteur;
       // 10 Sekunden Pause
      try{
        Thread.sleep(10000);
      }catch (Exception ignored){}
       // Der Zähler wird erhöht
      compteur=myCompteur+1;
    }//synchronisiert
     // wird zurückgesetzt
    return compteur;
  }//getCompteur

   // die beim ersten Laden der Seite ausgeführte Methode
  public void jspInit(){
     // Zähler initialisieren
    compteur=100;
  }
